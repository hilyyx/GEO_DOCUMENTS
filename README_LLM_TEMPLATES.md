# GEO Documents: генерация пояснительной записки через локальную LLM

## 1. Цель обновления

Нужно добавить в GEO Documents отдельный модуль, который умеет генерировать
пояснительную записку по выбранному шаблону на основе контекста уже сформированного
документа.

Пользовательский сценарий:

1. Пользователь собирает общий отчёт через текущий механизм склейки.
2. Пользователь выбирает шаблон пояснительной записки.
3. Приложение извлекает текстовый контекст из сформированного DOCX/PDF.
4. Шаблон превращается в структурированный промпт для локальной LLM.
5. LLM генерирует готовый текст пояснительной записки.
6. Пользователь проверяет/редактирует результат и сохраняет его в DOCX.

Важно: LLM работает локально через Ollama. После установки модели интернет не нужен.

## 1.1 Что реализовано сейчас

В текущей версии добавлен первый рабочий MVP:

- модуль шаблонов `geo_documents/template_model.py`;
- JSON-хранилище шаблонов `geo_documents/template_store.py`;
- генератор пояснительной записки `geo_documents/explanatory_generator.py`;
- окно редактирования и генерации `geo_documents/explanatory_dialog.py`;
- кнопка в главном окне `Пояснительная записка (LLM)`;
- стандартный шаблон `Пояснительная записка ИГИ`, создаётся автоматически;
- цельный текстовый редактор шаблона:
  - пользователь пишет полный текст пояснительной записки;
  - выделяет мышью нужные фрагменты;
  - красит выделение жёлтым или зелёным;
  - добавляет заметку/инструкцию к выделенному фрагменту;
  - рядом с фрагментом с заметкой появляется значок комментария `💬`;
  - по кнопке `Открыть заметку` можно открыть и отредактировать заметку у текущего
    цветного фрагмента или у значка комментария;
- генерация зелёных блоков по одному через локальную Ollama;
- сохранение результата в DOCX;
- опциональное сохранение жёлтой/зелёной подсветки в итоговом DOCX.

Внутри приложения выделенные фрагменты всё равно сохраняются как структурированные
блоки JSON. Пользователь этого не видит: он работает с цельным текстом, а приложение
само превращает цветные диапазоны в блоки для генерации промпта.

Неразмеченный текст используется только как визуальный каркас шаблона в редакторе.
В итоговую пояснительную записку он не записывается. В результат попадают только:

- жёлтые фрагменты (`fixed`) — без изменений;
- зелёные фрагменты (`generated`) — после заполнения LLM.

## 3. Термины

### Шаблон

Шаблон — это текст пояснительной записки с разметкой фрагментов.

В шаблоне есть:

- обычный текст;
- жёлтые фрагменты;
- зелёные фрагменты;
- заметки к любому выделенному фрагменту.

### Жёлтый фрагмент

Жёлтым выделяется текст, который должен остаться неизменным в каждой пояснительной
записке, построенной по этому шаблону.

Пример:

> Инженерно-геологические изыскания выполнены в соответствии с действующими
> нормативными документами.

Такой текст LLM не должна переписывать, сокращать или заменять.

### Зелёный фрагмент

Зелёным выделяется место, куда нужно подставить информацию, найденную в контексте
сформированного документа.

Пример:

> Инженерно-геологические изыскания по объекту: `[название объекта]`.

Если `[название объекта]` выделено зелёным, LLM должна найти название объекта в
исходном отчёте и вставить его на это место.

### Заметка

Заметка — это инструкция к выделенному фрагменту. Она помогает LLM понять, где искать
информацию и как её использовать.

Примеры заметок:

- `Искать в разделе 1.1 Введение`;
- `Взять заказчика из титульного листа или введения`;
- `Если точного значения нет, не выдумывать, оставить пометку [уточнить]`;
- `Сформулировать одним предложением`;
- `Использовать технический стиль без разговорных фраз`.

## 4. Пример по приложенному PDF

В примере `Отчет.pdf` структура пояснительной записки начинается так:

- `1. Пояснительная записка по инженерно-геологическим изысканиям`;
- `1.1 Введение`;
- сведения об объекте;
- договор;
- заказчик;
- проектировщик;
- идентификационные сведения;
- цель и задачи изысканий;
- `1.2 Изученность инженерно-геологических условий`;
- `1.3 Физико-географические и техногенные условия`.

Для такого шаблона можно разметить:

- постоянные нормативные формулировки — жёлтым;
- название объекта, номер договора, заказчика, проектировщика, адрес, цель работ,
  задачи работ, геоморфологическое описание — зелёным;
- к каждому зелёному фрагменту добавить заметку, из какого раздела брать значение.

## 5. Формат хранения шаблонов

Рекомендуемый формат — JSON-файл в папке проекта/пользователя.

Папка:

```text
templates/
  explanatory_notes/
    default_igi.json
    water_supply.json
    user_custom_1.json
```

Пример структуры:

```json
{
  "id": "default_igi",
  "name": "Пояснительная записка ИГИ",
  "description": "Базовый шаблон пояснительной записки по инженерно-геологическим изысканиям",
  "version": 1,
  "blocks": [
    {
      "id": "b1",
      "type": "fixed",
      "text": "1. Пояснительная записка по инженерно-геологическим изысканиям",
      "note": "Заголовок всегда сохранять без изменений"
    },
    {
      "id": "b2",
      "type": "fixed",
      "text": "1.1 Введение",
      "note": ""
    },
    {
      "id": "b3",
      "type": "generated",
      "text": "[описание объекта]",
      "note": "Найти название объекта, договор, заказчика и проектировщика в разделе 1.1 Введение"
    }
  ]
}
```

Типы блоков:

- `fixed` — жёлтый блок, неизменяемый текст;
- `generated` — зелёный блок, текст должен быть найден/сгенерирован по контексту;
- `plain` — обычный текст без специальной логики.

## 6. Почему лучше хранить шаблон не как DOCX

DOCX удобен для визуального редактирования, но сложен для надёжного хранения
инструкций к каждому выделению:

- выделение цветом в DOCX можно прочитать, но заметки и связь с конкретным фрагментом
  усложняют обработку;
- пользователь может случайно сломать XML/стили;
- сложнее делать версионирование шаблонов;
- сложнее строить промпт.

Лучший подход:

1. В приложении дать визуальный редактор шаблона.
2. Внутри хранить шаблон как JSON.
3. При необходимости экспортировать шаблон/результат в DOCX.

Позже можно добавить импорт DOCX-шаблонов, но как второй этап.

## 7. Интерфейс шаблонов

В приложении нужен новый раздел, например:

```text
Шаблоны пояснительной записки
```

Функции:

- создать новый шаблон;
- открыть существующий шаблон;
- сохранить шаблон;
- сохранить как новый шаблон;
- удалить шаблон;
- дублировать шаблон;
- выбрать шаблон для генерации;
- просмотреть заметки;
- редактировать заметки.

## 8. Редактор шаблона

В редакторе должен быть текстовый документ с возможностью выделить часть текста и
назначить тип:

- `Жёлтый / неизменяемый`;
- `Зелёный / заполнить из документа`;
- `Обычный текст`;
- `Добавить заметку`.

Минимальный вариант реализации в PyQt:

- `QTextEdit` или `QTextBrowser` как редактор;
- кнопки:
  - `Жёлтый`;
  - `Зелёный`;
  - `Очистить выделение`;
  - `Заметка`;
  - `Сохранить шаблон`;
- справа панель свойств выделенного фрагмента:
  - тип блока;
  - текст заметки;
  - id блока.

Визуально:

- жёлтый фон — `fixed`;
- зелёный фон — `generated`;
- обычный фон — `plain`.

## 9. Генерация промпта

Шаблон нельзя просто целиком отправлять в LLM. Нужно построить строгий промпт.

Логика:

1. Из итогового DOCX/PDF извлекается контекст.
2. Шаблон разбивается на блоки.
3. Для каждого блока:
   - `fixed` вставляется в результат без изменения;
   - `generated` превращается в задачу для LLM;
   - `plain` вставляется как обычный текст или как вспомогательный контекст.
4. LLM получает:
   - роль;
   - исходный контекст документа;
   - список переменных/зелёных блоков;
   - инструкции из заметок;
   - требование не выдумывать отсутствующие данные.

Пример промпта:

```text
Ты готовишь пояснительную записку по инженерно-геологическим изысканиям.
Работай только по предоставленному контексту.
Не выдумывай значения. Если информации нет, напиши [уточнить].

Контекст документа:
...

Шаблон:
1.1 Введение

Неизменяемые фрагменты:
- "Инженерно-геологические изыскания выполнены..."

Нужно заполнить:
1. [название объекта]
   Инструкция: искать в разделе 1.1 Введение.
2. [заказчик]
   Инструкция: искать в титульном листе или разделе 1.1.
3. [цель изысканий]
   Инструкция: искать рядом с фразой "Целью изысканий являлось".

Верни готовый текст раздела без комментариев.
```

## 10. Два возможных режима генерации

### Режим 1. Генерация всего текста одним запросом

Плюсы:

- проще реализовать;
- быстрее получить первый результат;
- удобно для коротких шаблонов.

Минусы:

- маленькие локальные модели могут ошибаться;
- большой контекст может не поместиться;
- сложнее контролировать каждую зелёную вставку.

### Режим 2. Генерация по блокам

Каждый зелёный блок генерируется отдельно.

Плюсы:

- лучше контроль;
- легче отлаживать;
- можно показывать пользователю, что именно найдено;
- меньше расход RAM и контекста.

Минусы:

- больше запросов к LLM;
- генерация дольше.

Рекомендуется для GEO Documents: режим 2.

## 11. Рекомендуемый пайплайн генерации

```text
Итоговый отчёт DOCX/PDF
        ↓
Извлечение текста и секций
        ↓
Выбор шаблона
        ↓
Разбор блоков шаблона
        ↓
Для каждого зелёного блока:
  - найти релевантный контекст
  - применить заметку
  - отправить запрос в LLM
        ↓
Сборка финальной пояснительной записки
        ↓
Предпросмотр
        ↓
Сохранение DOCX
```

## 12. Поиск информации в документе

Чтобы LLM не получала весь отчёт каждый раз, нужен предварительный поиск.

Минимальный вариант:

- разбить текст документа по заголовкам:
  - `1.1 Введение`;
  - `1.2 Изученность...`;
  - `1.3 Физико-географические...`;
  - и т.д.;
- если в заметке указан раздел, брать только этот раздел;
- если раздел не указан, брать первые несколько релевантных фрагментов по ключевым словам.

Например:

Заметка:

```text
Искать в разделе 1.1 Введение, рядом со словами "Заказчик" и "Проектировщик".
```

Тогда в промпт попадает только фрагмент раздела 1.1, а не весь документ.

## 15. Генерация итогового DOCX

После генерации нужно сохранять результат:

- как `.txt` для простого теста;
- как `.docx` для пользователя;
- позже можно вставлять пояснительную записку обратно в общий отчёт.

Минимальный DOCX:

- заголовки;
- обычные абзацы;
- сохранение постоянного текста;
- подстановка сгенерированных зелёных блоков.

## 16. Работа с цветами

В редакторе:

- жёлтый = неизменяемый блок;
- зелёный = генерируемый/подставляемый блок.

В итоговом документе можно сделать два режима:

1. Чистовой режим:
   - цвета убираются;
   - остаётся обычная пояснительная записка.

2. Режим проверки:
   - жёлтые и зелёные подсветки сохраняются;
   - пользователь видит, какие места были сгенерированы.

Рекомендуется добавить чекбокс:

```text
Сохранять подсветку в результате
```

## 17. Работа с заметками

Заметки не должны попадать в чистовой результат.

Они используются только:

- для генерации промпта;
- для подсказки пользователю в редакторе;
- для отладки.

В UI заметку можно показывать:

- при клике на выделенный фрагмент;
- в правой панели;
- в виде всплывающей подсказки.

## 18. Локальные модели

Сейчас проверены варианты через Ollama.

Для слабых ПК:

```powershell
ollama pull gemma3:1b
```

Для более мощных:

```powershell
ollama pull gemma4:e2b
```

Для хороших ПК:

```powershell
ollama pull gemma4:e4b
```

В приложении нужно дать настройку:

```text
Модель Ollama: [gemma3:1b]
```

и кнопку:

```text
Проверить модель
```

## 19. Ошибки и защита

Нужно обработать:

- Ollama не установлена;
- Ollama не запущена;
- модель не скачана;
- недостаточно RAM;
- LLM не нашла данные;
- шаблон повреждён;
- документ не содержит нужного раздела;
- пользователь удалил выделенный блок.

Если данных нет, LLM должна писать:

```text
[уточнить]
```

а не выдумывать.

## 21. Предлагаемый порядок разработки

### Этап 1. Ядро шаблонов

- `template_model.py`;
- `template_store.py`;
- загрузка/сохранение JSON;
- тестовый шаблон пояснительной записки.

### Этап 2. Промпты

- `template_prompt.py`;
- сбор промпта из шаблона;
- применение заметок;
- генерация одного зелёного блока.

### Этап 3. Контекст документа

- разбиение документа на разделы;
- поиск по названию раздела из заметки;
- fallback-поиск по ключевым словам.

### Этап 4. Генерация результата

- генерация всех зелёных блоков;
- сборка финального текста;
- сохранение в DOCX.

### Этап 5. UI

- вкладка/кнопка `Пояснительная записка`;
- выбор документа-контекста;
- выбор шаблона;
- кнопка `Сгенерировать`;
- предпросмотр результата.

### Этап 6. Редактор шаблонов

- создание шаблона;
- редактирование текста;
- выделение жёлтым/зелёным;
- заметки к выделениям;
- сохранение шаблона.

## 22. Главный риск

Главный риск — качество генерации на маленьких локальных моделях.

Поэтому нужно:

- не просить модель писать весь отчёт с нуля;
- давать маленькие точные задачи;
- использовать заметки;
- генерировать по блокам;
- показывать результат пользователю перед сохранением;
- оставлять `[уточнить]`, если данных нет.
